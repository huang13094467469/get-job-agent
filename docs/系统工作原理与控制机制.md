# Get-Job Agent · 系统工作原理与控制机制

> 本文聚焦一个核心问题：**一套求职 Agent 是怎么"在一个真实招聘网页里自主干活、又始终被控制在安全范围内"的**。
> 与 README 的功能概览不同，本文讲透运行原理、链路时序与控制手段，方便后续维护与排障。

---

## 0. 一句话原理

整个系统是 **"大脑"与"手"分离的计算机视觉式（computer-use）协作**：

- **大脑（DeepAgent，跑在本地 FastAPI Server）**：负责"看、决策、复核"。它不打页面，只读懂页面的**结构化快照**，然后决定"下一步做什么"。
- **手（Content Script，注入 BOSS 直聘页面的 Chrome 扩展脚本）**：负责"执行"。它不会思考，只会按指令逐字操作真实 DOM，并把结果回传。
- 两者通过 **一条 WebSocket 长连接 + 一套"发指令→等回执"的桥接协议** 通信，反复形成 **`看快照 → 决策 → 执行 → 看变化 → 再决策`** 的闭环。

```
┌───────────── 大脑 · Agent Server (FastAPI, 127.0.0.1:8791) ─────────────┐
│  DeepAgent 图 (LangGraph)                                              │
│   LLM(DeepSeek/Qwen) ◄──────── 系统提示 + 长期记忆 + 技能                 │
│    │  iterate                                                        │
│    ▼                                                                    │
│  工具层 browser_snapshot / browser_act / start_chat / send_greeting     │
│    │                                                                  │
│    ▼  PageActionBridge（发指令→await 回执）                              │
├─────────────────────── WS 定向中继（hub）───────────────────────────────┤
└──────────────────────────────▲──┴──────────────────────────────────────┘
                    dom 指令  │  │  dom_result 回执
                             ▼  ▲
━━━━━━━━━━━━━━━━━━━━━━━━ 真实浏览器（Chrome 薄壳 MV3）━━━━━━━━━━━━━━━━━━━
┌───────────────────────── 手 · Content Script（注入 zhipin 页面）─────────┐
│  snapshot: 遍历可见可交互元素 → 生成带 ref 的快照                          │
│  act     : click / type / select / scroll / navigate ...               │
│  send_greeting / start_chat: 高层 DOM 原语                              │
└──────────────────────（复用页面已登录的 HTTP 会话）───────────────────────┘
```

## 1. 组件与职责

| 角色 | 载体 | 职责 | 关键设计点 |
|---|---|---|---|
| **Agent 大脑** | `harness.py` → `create_deep_agent` | 循环决策、调用工具、撰写话术 | 单例编译图，多 thread 复用 |
| **浏览器工具** | `agent/tools/browser_ops.py` | 把"看/做"暴露成 LLM 可调的工具 | 写类工具走护栏/去重 |
| **桥接原语** | `api/page_bridge.py` | 命令→回执的同步 await 通道 | asyncio.Future 账本 |
| **WS 中枢** | `api/routes/ws.py` | 转发指令、回传结果、驱动无人值守 | 定向中继 + 生命周期路由 |
| **浏览器执行** | `extension/content/content.js` | 真实 DOM 操作 | 唯一执行器，复用登录态 |
| **运行护栏** | `runtime_guard.py` / `state.py` | 投递上限、去重、计数持久化 | 迁入自定义 state |
| **持久化** | `infra/checkpoint.py`（Postgres） | 会话/护栏计数跨重启保留 | AsyncPostgresSaver |
| **观测** | `observability.py` / `core/config.py` | 运行追踪、上下文统计、限额 | 中间件 + LangSmith |

> ⚠️ 关键约束：**页面上的真实交互（点击/输入/发送）只允许 Content Script 做**，Agent 从不直接操作浏览器。这种单一执行器设计让"可控性"全部收口在 Server 侧——想拦住一切风险动作，只需在 Server 的工具层把关。

## 2. 核心链路：一次"看→做"的完整时序

以 Agent 决定「点一下【立即沟通】」为例，走一遍全链路（对应 `browser_act`）：

```
步  Agent 大脑                     PageActionBridge        WS 中枢(hub)              Content Script
──  ──────────────────────────    ────────────────       ─────────────         ─────────────────
1  browser_act(op=click, ref) ──► bridge.act() 生成 idem
2                                  登记 asyncio.Future
3                                  ── 发 dom 指令 ──────► route_to_page ──────► 接收指令
4                                  (此时 await 等待)                             找到元素 → 点击 → 等页面沉降
5                                                                下一帧 dom_result(idem=...)◄── 回传
6                                  ◄── resolve() 命中 idem ──────────
7                                  填充 Future → await 返回
8  _fmt_result: 精简变化量 ◄────   {ok, updated:快照元素}
9  把"变化量"写回 context，供模型复核
```

几个必须理解的点：

### 2.1 为什么需要桥接层（page_bridge）
原本页内 Content Script 的回执只能 "按 idem 回发给发起面板"，但 **DeepAgent 的工具不是面板**。桥接层用 `idem -> asyncio.Future` 账本，让工具在同事件循环里发指令后直接 `await`，`dom_result` 到达时 `resolve()` 填充 Future——对外表现为一次普通的异步工具调用。

### 2.2 idem（幂等号）决定了"这条回执归谁"
每条指令带一个唯一 `idem`。页内回执时带同样的 idem，桥接层据此命中 pending 的 Future，`resolve()` **消费掉**这条回执（不再广播给面板）。面板发起的指令则按 idem 路由回该面板——同一个枢纽协议支撑两条不同链路。

### 2.3 页面离线 / 超时的结构化处理
桥接层把**异常转成结构化文案**（而非抛异常打断 Agent）：
- 页面未连接 → `{ok:false, error:"page_not_connected:zhipin", suggest:"请先打开 Boss 页面"}`
- 指令超时 → `{ok:false, error:"page_action_timeout"}`

这保证 Agent 面对断连能把"软失败"当成可纠正信号来自我调整，而不是整段崩掉。

### 2.4 回传"变化量"而非整页快照
`_fmt_result` 会对 act 回填做 **compact 精简**：只保留本次**新增/变化的元素** ∪ 关键动作按钮（如"继续沟通"），并且过滤掉已处理过的岗位。这样每次操作喂给模型的是"刚改变了什么"，大幅压 token、聚焦注意力，避免整页快照二次看页。

## 3. 浏览器操作四工具：大脑给模型的手柄

> 在 `browser_ops.py` 里，有 **4 个 `@tool` 装饰的异步工具**暴露给 LLM，是"大脑"唯一能"碰到页面"的通道。它们不直接操作 DOM，而是 **把请求桥接到 Content Script 的原语上**（经 `PageActionBridge.act` → WS → content.js 的 `domHandlers`），再按需精简返回。理解这四把工具，就理解了 Agent 决策期走哪条路、会得到什么反馈。

四工具与 Content Script 原语、以及"读写性质"的对照：

| 工具 | 对应 content.js 原语 | 性质 | 一句话职责 |
|---|---|---|---|
| `browser_snapshot` | `snapshot` | 读 | 决策前"看"整页（过滤已处理岗位） |
| `browser_act` | `act` | 读/写 | 执行一步操作并返回"变化量" |
| `start_chat` | `start_chat` | 写 | 确定性进入某岗位聊天页 |
| `send_greeting` | `send_greeting` | **写·真实外发** | 唯一能向 HR 发话术的工具 |

---

### 3.1 browser_snapshot —— "看一眼"

**入参**：`goal_hint`（仅提示本次目标，可忽略）

**如何工作**：
```
@tool browser_snapshot()
  → _bridge_act("snapshot", {"max": 80})     // 桥接到 content.js 的 snapshot 原语
  → content.js: 生成可访问性快照（元素+岗位+页面态）   [见第 4 章]
  → _fmt_result(): _prune_snapshot(compact=False)  // 顶层快照：过滤已过目/已打招呼岗位、元素截前 80 个
  → 返回 {ok, data:{url,title,page,elements,jobs?}}
```

**关键点**：
- 它走 `domHandlers["snapshot"]`，即"第 4 章看懂"那套逻辑；
- 顶层用 `compact=False` → **保留全量精简元素**（但不含已处理岗位），是"主动看整页"；
- 适合用在：**任务开始、导航后、或对页面结构不确定时**——"重新看整页"。

**Agent 的使用习惯**：每次决策前先调用它"看"页面，元素自 `ref` 可引用。

---

### 3.2 browser_act —— "做一步"

**入参**：`op` + 定位参数（`ref` / 可选 `match_text`+`within_text`+`occurrence` 兜底）+ 载荷（`text`）

**如何工作**：
```
@tool browser_act(op, ref, text, match_text, within_text, occurrence)
  → 校验：op=="type"且 text 超 500 字 → 直接返回 {ok:false, error:"text_too_long"}（先拦不做）
  → _bridge_act("act", {op, ref, text, match_text, within_text, occurrence})
  → content.js: 三级定位元素 → 执行 op 对应 DOM 操作 [见第 5 章]
  → _fmt_result(): compact 精简 —— 只保留"本步新增/变化元素"∪关键动作按钮
  → 返回 {_action:"act:<op>@<target>", ok, data:{updated:{elements:[...]}}}
```

**关键点**：
- 它是**唯一通用执行器**，`op` 分发（click/type/select/scroll/press/go_back/navigate/wait/load_more），详见第 5.2 原语表；
- **返回的是"变化量"不是整页**：`compact=True` 只回填新增/变化元素，模型拿到的永远是最小增量，省 token；
- 定位三级退让：`ref → data-bs-ref → match_text(within_text, occurrence)`，抗 SPA 重渲染（见 5.1）；
- 属于"写"类工具，会真实触发页面交互，文档标注「这是写类操作，会真实触发页面交互」。

**Agent 的使用习惯**：对目标执行精确一步；不为"看一眼"而再调 snapshot（操作后变化已含在返回里）。

---

### 3.3 start_chat —— "一步进聊天页"

**入参**：`within_text`（岗位名，锁定具体卡片）+ `occurrence`（可选）

**如何工作**：
```
@tool start_chat(within_text, occurrence)
  → _bridge_act("start_chat", {within_text, occurrence}, timeout=12s)
  → content.js: 确定性进入聊天页的状态机 [见第 5.6 节]
        已在聊天页 → {reached_chat:true, phase:'already_chat'}
        点【立即沟通】→ 若弹框→点【继续沟通】→ 轮询到 /web/geek/chat
  → 返回 {_action:"start_chat", ok, reached_chat, phase, ...}
  → 若超时/瞬断：标记 ok:false, retry:true, do_not_skip:true + hint（先 snapshot 验证，切勿跳过本岗位）
```

**关键点**：
- 这是 **"把多步脆弱的进聊天页操作从模型手里收回来"** —— 模型只需说"沟通这岗"，内部自动处理【立即沟通】→【继续沟通】弹框→轮询，不依赖模型去猜弹框怎么点；
- 返回的 `phase` 是给 Agent 的导航信号：
  - `reached_chat=true` → 可直接 `send_greeting`
  - `phase=navigating` / `confirm_clicked` → 先 `browser_snapshot` 确认到聊天页再发
  - `no_immediate_chat_button` → 该岗位无按钮/已沟通
- **超时/瞬断 ≠ 没按钮**：点击可能已生效、页面在跳转，故强制 `do_not_skip:true`，杜绝因超时误弃达标岗位（SSO 页跳转的经典坑）。

---

### 3.4 send_greeting —— "唯一向 HR 发话术"

**入参**：`text`（为当前岗位拟好的打招呼话术）+ 注入的 `runtime: ToolRuntime`

**如何工作**：
```
@tool send_greeting(text, runtime)
   ① 前置拦截（都不发，返回结构化 ok:false + suggest）：
       - text 空 / 超 300 字
       - 已达投递上限 greeting_count >= max_greetings_per_run  → greeting_cap_reached（让 Agent 收尾）
       - 话术重复 sent_hashes 命中                          → duplicate_greeting
       - 同「公司|岗位」已登记终态（已打招呼）               → already_greeted
   ② 桥接执行：
       _bridge_act("send_greeting", {text})
       → content.js: 硬校验"真在聊天页"→ 填话术 → 点【发送】/Enter → 以"输入框清空"判发出 [见 5.6]
   ③ 成败判定：以 content **内层 data.ok 为准**（外层 ok 只表示 dispatch 成功，
      会误把 not_on_chat_page/未找到输入框 当"已发送"）
   ④ 成功才记账：Command(update) 写 greeting_count+1、sent_hashes+[指纹]，并登记 job_ledger「已打招呼」
   → 返回 ToolMessage + state 更新（经 Command 写回 thread checkpoint）
```

**关键点（这是全系统最重护栏的工具）**：
- **唯一真实外发通道**——系统提示铁律"所有真实对外发送只能调用 send_greeting"，把"对外动作"从模型手里完全收口到一个可审计点；
- **两类模式**：confirm → 触发框架原生 HITL 暂停（`interrupt_on`），你批准/修改/拒绝后再 `Command(resume)` 恢复同一 thread；unattended → 不到上限就自动发送；
- **护栏计数持久**：`greeting_count` / `sent_hashes` 不是内存变量，而是 **`JobAgentState` 里的字段，随 Postgres checkpoint 持久**——重启不归零，防止无人值守突破上限；
- **成功判定很谨慎**：只看 Content Script 内层 `data.ok`（例如 `not_on_chat_page` 这种软错误要透出让模型纠正），且**只有确认发出才计数 + 记账**，避免"假成功"污染"已打招呼"清单。

## 4. Content Script 如何"看懂"浏览器页面

> 这是整个方案的地基：**LLM 不吃像素，只吃结构化文本**。Content Script 的核心职责是把"一个 live 的、视觉的网页"降维成"一段模型能读懂的、可投递的**可访问性快照（accessibility snapshot）**。它不是截图，也不是读 innerHTML，而是按一套规则自省 DOM、挑出"值得看的交互元素"并编成稳定的引用。

### 4.1 为什么能"看懂"——MV3 隔离世界的自省窗口

Content Script 运行在 **isolated world（隔离世界）**：它和页面 JS 不在同一全局作用域，但**共享同一个 DOM**。这恰好是"看懂"的合法性来源：
- 它可以用 `document.querySelectorAll` / `TreeWalker` **读取页面结构与可交互元素**——这不被页面 JS 干扰，也不被页面 CSP 挡（CSP 管的是脚本执行，不影响 DOM 读取）；
- 它还能随页面**复用用户已登录的 HTTP 会话**（cookie 在浏览器层），这是它能在登录后的 BOSS 页面上操作的根基。
- 反过来说，**页面自己的 JS 摸不到 Content Script 的全局变量**，也就无法轻易反制它的快照逻辑。

### 4.2 三件套：抓取 → 过滤 → 打标（生成快照的前半程）

第一步 `collectElements(max)` 是"看懂"的核心，分三步：

**① 抓取（TreeWalker 深度优先遍历）**
用 `document.createTreeWalker(body, NodeFilter.SHOW_ELEMENT)` 按 **DOM 树深度优先顺序**扫一遍。这个顺序是**固定且确定的**——它是后续 `ref` 编号与重定位一致性的根基。

**② 过滤（snapRelevant）——敢不敢入选**
每个元素要过四关才算"值得看"：
| 关卡 | 判定 |
|---|---|
| 是元素节点 | `nodeType === 1` |
| 属于可读标签 | 排除 `script/style/noscript/template` |
| **可见**（`isVisible`） | `getComputedStyle` 非 `display:none`/`visibility:hidden`/`opacity:0`、非 `aria-hidden`、非 `disabled`、`getBoundingClientRect()` 有宽高 |
| **有内容/可交互** | 交互元素 label 非空；或非交互但"无子元素的短文本叶子且文字≤80字符" |

注意这个规则**刻意省略了大量节点**（容器 div、图片、无意义的包裹层），把快照从"几万节点"压到"几十个可操作点"，模型才不会淹没。**代价是快照只是"够用"的精简视图，不是完整 DOM**——这正是为什么叫"可访问性快照"而非"整页序列化"。

**③ 打标（筛出可操作目标）**
对入选的每个元素提取：
- `ref`：**确定性 DOM 顺序索引** `e0,e1,e2…`（由"同一次过滤判定"逐次递增，保证重定位时序号一致）
- `role`：由 `tag`/`aria-role`/`type` 推导（button / link / textbox / listbox …）
- `text`（label）：**精简 label**——只取"自身直接文本"（直接子文本节点）+ `aria-label`/`title`/`placeholder`，**绝不取整棵子树文本**，降噪省 token
- 交互性有额外价值：若元素无 `id`/`name`，则给它打一次性 `data-bs-ref="eX"` 锚点

**④ 变化标注 `new`**
每次快照记录一份"元素签名集合" `lastSigSet`（签名=`tag|role|label`）。下次快照时，**凡是签名不在上一轮集合里的元素标 `new:1`**。这给了模型一个信号：**"这轮新出现了什么"**——尤其帮它注意到 SPA 随机弹出的【继续沟通】这类隐藏元素。

### 4.3 快照长什么样（输出三层）

`snapshot()` 返回三层，交给上游 `_prune_snapshot` 过滤后送入模型：

```
{
  url, title, page: chat/detail/list/other, scroll: {y, h}
  elements: [ {ref, tag, role, text, new?},
              {ref:"e0", tag:"button", role:"button", text:"立即沟通"},
              {ref:"e7", tag:"a", role:"link", text:"Java工程师 (2-5年)"} ],
  jobs?: [ {name, company, salary, area, tags, contacted} ]   // 仅列表页，结构化抽取岗位
}
```

- `elements`：通用可操作点，是 Agent "对页面做任何事"的对象；
- `jobs`：列表页专属的**语义化岗位清单**（含 `contacted` 已沟通标记）——让模型不只看到"有个按钮"，还看到"这是哪个公司、哪个岗、达不达标"；
- 上游还会按"已过目/已打招呼"过滤掉已处理岗位，避免重复关注。

### 4.4 对比：为什么不用坐标 / 截图 / XPath

| 方案 | 能看懂吗 | 问题 |
|---|---|---|
| 截图 + 视觉模型 | 能 | 依赖视觉模型、token 极贵、无法直接点元素 |
| XPath / CSS 选择器 | 依赖具体页面结构 | SPA 重渲染即失效、绑定平台 |
| **可访问性快照 + ref** | ✅ | 轻量、稳定、与"操作"共用一套定位 |

`ref` 这套方案的优雅在于：**"看懂"和"操作"共用同一套 ref 坐标系**——快照里看到的 `e0`，操作时直接说"点 `e0`"即可，天然闭环。

## 5. Content Script 如何"操作"浏览器页面

看懂之后要能"点得下去"。Content Script 的操作分两层：**定位（locate）** 与 **原语执行（act）**。

### 5.1 定位一套元素：ref → data-bs-ref → 文本兜底

操作前必须先拿到目标元素，链路是**三级定位**：

1. **按 ref 直接找**：`document.querySelector('[data-bs-ref="eX"]')`。这是最常用路径——`ref` 即快照里看到的那个。
2. **退化"按 DOM 顺序补位"**：若锚点丢了但 `data-bs-ref` 还在页面某处已被 SPA 改（或被过滤掉），则用 `parseInt(ref)` 回到"按同样 `snapRelevant` 判定数到第 idx 个元素"——**只要过滤规则不变，序号就稳定**，这就是 `ref` 与 `collectElements` 共享判定 `snapRelevant` 的原因。
3. **文本稳健定位 `findByText(match_text, within_text, occurrence)`**：把定位从"结构"转为"语义"，抗重渲染：
   - 第一遍：`TreeWalker` 扫**可见 + 语义可交互**且 `label` 包含 `match_text` 的元素；
   - 第二遍兜底：弹框里的【继续沟通】常是非语义 `div/span`（靠 `addEventListener`），第一遍扫不到——再扫**可见的短文本叶子**，命中后 `_clickableSelfOrAncestor` **上溯到可点击祖先**；
   - `within_text`：再校验命中元素的祖先链文本是否包含它（如"Java工程师"），用于锁定**某一具体岗位卡片**里的那个按钮；
   - `occurrence`：同命中多个时取第几个。

### 5.2 原语执行表（act 的分发）

`act(op, ref, ...)` 按 `op` 分发到不同 DOM 操作：

| op | 具体实现 | 关键点 |
|---|---|---|
| `click` | `_safeClick(el)` → `el.click()` | 见下方"导航安全" |
| `type` / `select` | `setNativeValue` + 派发事件 | 见下方"受控组件原理" |
| `press` | 派发 KeyboardEvent `keydown/keyup`（默认 Enter） | 触发键盘事件监听 |
| `scroll` | 找内层滚动容器（`findJobListScroller`）`scrollTop += amount` | Boss 列表是内层容器无限加载，**window 滚动驱动不了它** |
| `load_more` | 反复滚到底 + `waitForSettle`，直到卡片数不再增长 | 触发无限加载翻页 |
| `navigate` / `go_back` | `location.href=` / `history.back()`，排到下一 tick | 见"导航安全" |
| `wait` | 轮询 URL / 选择器 / 文本出现 | 主动等待页面就绪 |

**为什么操作后必带快照**：每个 `act` 返回里都带 `updated: snapshot()`——这就是"看→做→**复核**"闭环的"复核"环节。Agent 上一次快照是"操作前"，这次拿到"操作后"，一比就知对不对。

### 5.3 受控组件原理：为什么不能直接 `el.value = text`

Boss 是 **React/Vue 等受控表单**的大户。直接赋值 `input.value = '你好'` **不会触发**受控组件的 `input`/`change` 事件监听，框架不会把它当作"用户真的输了"：
```js
el.value = '你好'                 // ❌ React 状态不同步
setNativeValue(el, '你好')        // ✅ 走原生 value setter + 派发事件
```
`setNativeValue` 的正确姿势是：**用原型链上的原生 value setter**（`Object.getOwnPropertyDescriptor(HTMLInputElement.prototype,'value').set`）做赋值，再 `dispatchEvent(new Event('input'))` + `dispatchEvent(new Event('change'))`。这样既绕过 React 对 value 属性的拦截，又让框架级监听器能感知输入。`contenteditable` 输入框则直接改 `innerText` + 派发 `input`。

### 5.4 导航安全：SPA 跳转不回执的经典坑

Boss 是 SPA，点【继续沟通】/【立即沟通】可能触发**整页跳转**，旧页销毁会连事件循环一起杀掉，导致 `dom_result` 发不出去、Server 侧 20s 超时。Content Script 的处理：
1. 点击前挂 `pagehide` 监听 + **压制 `javascript:`/空 href/`#` 锚点**（否则自带 CSP 会报 "Running the JavaScript URL"）；
2. 点击后短探 `pagehide` 或 `location.href` 变化 → 一旦变，**立即回执** `{navigating:true}`（不等快照，因为旧页要没了）；
3. Server 端收到 `navigating` 就把它当"正在跳转"告诉 Agent：**下一步 `browser_snapshot` 看新页**，而不是误判"没操作成功"。

### 5.5 等页面安定：waitForSettle（MutationObserver 代替固定 sleep）

固定 `sleep()` 很蠢——快则浪费时间、慢则没到位。`waitForSettle` 监听 `document.body` 的 **MutationObserver**（子节点/属性/文本都监听）：只要连续 `idle`（默认 300ms）无 DOM 变动就认为"页面沉降完成"，并有 `max`（默认 2500ms）硬上限兜底。让点击后的异步渲染真正完成再取快照。

### 5.6 高层复合原语：start_chat / send_greeting

**把多步脆弱操作从模型手里收回**为确定性的一个工具：

- `start_chat`（一个动作进聊天页）：点【立即沟通】→ 若弹【已向BOSS发送消息】则点其中【继续沟通】→ **轮询**（每 250ms）直到 URL 到 `/web/geek/chat` 或出现聊天输入框。全程用 `findByText` 处理弹框，导航中即时回执。
- `send_greeting`（唯一真实外发）：
  1. **硬校验**：必须先真进入聊天页且有可见输入框（`firstVisibleSel`），否则不发的理由写清楚——避免在列表/详情/弹框上"假装发送成功"；
  2. 填话术（受控组件方式）；
  3. 优先点【发送】按钮（选择器→文本兜底）→ 失败按 Enter → 再点一次；
  4. **以"输入框是否被清空"判真实发出**（发送成功通常清空输入框）——`sent_cleared()` 为真才算成功，否则返回 `send_not_confirmed`，绝不误标"已打招呼"污染账本。

## 6. 控制机制（重点）：System 如何"管住" Agent

系统有**四层控制**，从"微观单步"到"宏观整轮"层层收口。

### 6.1 层① 精准决策导向：系统提示 + 长期记忆 + 工具护栏

- **系统提示精简**：只交代身份、铁律（所有真实外发只能走 send_greeting；以工具返回为准），避免污染意图。
- **长期记忆（AGENTS.md）+ 技能（SKILL.md）**：完整 SOP、风控、话术规范放 memory/skills，按需加载，不硬塞 system prompt。
- **`memory=` 常驻注入**：Agent 每步都能看到主流程 SOP；skills 按需激活进阶打法。
- **工具层护栏**（`send_greeting` 内）：
  - 话术空 / 超长校验
  - **投递上限**：`max_greetings_per_run`（默认 20），达上限即拒发并让 Agent 收尾
  - **话术去重**：相同话术 sha1 指纹，同会话只发一次
  - **已打招呼拦截**：同「公司|岗位」已登记终态则跳过

### 6.2 层② 运行期软错误自愈：中间件

`harness.py` 装配的中间件栈（顺序即执行顺序）：

| 中间件 | 作用 |
|---|---|
| `RunTraceMiddleware` | 全链路观测（本地 / LangSmith） |
| `TodoListMiddleware` | 强制 Agent 建任务清单，防跳步 |
| `ModelCallLimitMiddleware` / `ToolCallLimitMiddleware` | **单段模型调用/工具调用上限**，封死失控死循环 |
| `BrowserToolRetryMiddleware` | 浏览器工具软错误（ok:false）瞬时退避重试 |
| `ToolErrorMiddleware` | 非浏览器工具的可恢复异常转 error ToolMessage 让模型自愈 |
| `SummarizationMiddleware` | 超 30k token 自动压缩旧对话 |
| `compact_conversation` 工具 | 主动压缩，防上下文膨胀 |

### 6.3 层③ 会话级状态持久：护栏计数不靠内存

投递计数 / 话术指纹 / 暂存岗位**全部迁入自定义 state（`JobAgentState`）**，随 Postgres checkpoint 持久：

- 原进程级全局 dict 重启即失忆 → 现在 `greeting_count` / `sent_hashes` / `pending_job` 按 thread_id 隔离、跨重启保留
- 工具经注入的 `ToolRuntime` 读 `runtime.state`，用 `Command(update=...)` 写回
- 配持久 `AsyncPostgresSaver` 后，无人值守中途崩溃可**从 checkpoint 精确续跑**，计数不归零

### 6.4 层④ 整轮驱动：confirm 与 unattended 双模式

`ws.py` 的 `_run_agent_turn` 是整轮运行的"调度循环"，按模式走不同策略：

**confirm（人工确认）模式：**
- 每次 `send_greeting` 触发原生 HITL → Agent 在发送前暂停，抛出 `__interrupt__`
- Server 解析中断内容，推 `kind=interrupt` 事件给面板，展示"批准/修改/拒绝"三按钮
- 用户选择后 → 面板发 `agent_resume` → Server 以 `Command(resume)` 恢复**同一 thread**

**unattended（无人值守）模式：**
- 不挂 HITL，`send_greeting` 自动发送
- `_run_agent_turn` 跑完一段后自动续跑：只要**没报错/没中断/没输出结束哨兵/没触投递上限/没超最大步数**，就向同一 thread 注入 `_CONTINUE_MSG` 继续处理下一个岗位
- 结束条件（满足任一即收尾）：
  1. Agent 输出哨兵 **`【求职任务结束】`**
  2. 已达投递上限
  3. 已达 `_MAX_AUTO_STEPS`（60 段）
  4. 单段触达 `ModelCallLimit`

> 这张"结束判定表"是无人值守不失控的关键：**上限不是靠"让它别做了"，而是靠"满足条件就停 + 干净结束信号"双保险**。

## 7. 两种模式一图看懂

```
confirm 模式：                        unattended 模式：
用户下目标 ─┐                          用户下目标 ─┐
 Agent 逐岗跑 ──┐                        Agent 逐岗跑 ──fast/clean──► 处理下一岗
   ├─ 到 send_greeting ──╔══停══╗           ├─ 到达上限 / 无达标 ──► 输出哨兵，停止
   │                     ║ 等确认 ║         └─ 软错误 ──► 退避重试/纠正
   │   批准/修改/拒绝 ◄───╚═══╝→ Command(resume) 继续同一 thread
   └─ 继续下一岗
状态全程由 checkpointer 按 thread_id 持久（崩溃可续跑、HITL 可暂停数天后精确恢复）
```

## 8. 旁路：其他不在 Agent 主循环内的能力

- **在线简历画像**（`online_resume`）：Content Script 读平台在线简历 → Server `build_from_online`（解析/抽取/校验/入库/向量化）→ 广播给面板。
- **岗位过滤引擎**（`filter_jobs`）：面板提交岗位+规则 → Server 侧 `job_filter` 加权打分。
- **简历目录重扫**（`resume_build_dir`）：手动触发附件目录扫描，作简历"单一事实源"。
以上均走同一条 WS 协议，但**不经过 Agent 图**，与主闭环解耦。

## 9. 一手排障速查（常见"不对了"对应哪一环）

| 现象 | 大概率环节 | 排查点 |
|---|---|---|
| 工具返回 `page_not_connected:zhipin` | 手不在线 | 浏览器是否开了 BOSS 页、CS 是否注册 |
| 工具返回 `page_action_timeout` | 桥接回执丢失 | SPA 跳转销毁旧页？看是否 navigating 状态 |
| 一直重复同一个岗位/不走下一步 | 记忆/记账 | job_ledger 是否把该岗记为终态、去重是否误判 |
| Agent 突然结束 | 触达某上限 | 看是哨兵 / 投递上限 / 步数 / ModelCallLimit 哪个 |
| 重启后计数还在 | — | Postgres checkpoint 正常（`AsyncPostgresSaver`） |
| 无人值守没发几条就停 | 投递或限额 | `max_greetings_per_run` 是否设过小 |
